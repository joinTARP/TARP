# 游戏房间存档格式

房间默认位于 `~/.tarp/sessions/<房间 ID>/`，可通过 `TARP_HOME` 改变应用根目录。

开发版本仅支持当前存档格式，不提供不同开发版本之间的兼容读取或自动迁移。

## 文件职责

| 文件或目录                           | 职责                                             |
| ------------------------------------ | ------------------------------------------------ |
| `adventure.json`                     | 房间资料、玩家笔记、开局进度与队伍状态           |
| `settings.json`                      | 创建时复制的游戏配置，及冒险内独立调整           |
| `module/`                            | 编译的完整基础模组，游戏工具只读，可手动同步替换 |
| `module-source.json`                 | 本机模组来源目录，可首次绑定，不进入玩家同步     |
| `.module-sync/`、`.module-sync.json` | 模组同步候选、旧副本与发布恢复标记               |
| `game/`                              | 本局字段覆盖与新增文档，初始为空                 |
| `document-references.json`           | 可重建的文档声明引用索引                         |
| `session.sqlite`                     | 聊天消息、历史分页与持久插话队列                 |
| `agent/*.jsonl`                      | Pi 主持与队友会话                                |
| `playtest.json`（可选）              | MCP 临时预演的前置数据、初始结果与步骤记录       |

`session.sqlite` 的 `chat_messages` 保存消息的最新完整状态，`chat_requests` 保存普通发送与继续的请求身份、输入摘要和结果消息 ID，唯一键为 `(player_id, operation, request_id)`。请求记录与消息及待提交集合消费共同提交，随冒险保留；重启后重试返回已有消息的最新状态，不重复启动模型。`steering_requests` 保存插话及已撤销、已接收请求的终态，`steering_batches` 保存交接批次与显式提交请求去重，`steering_meta` 保存队列快照版本。Kysely 另维护迁移记录和迁移锁。玩家消息的 `chatOnly` 表示不作为指令提交给主持人；聊天增量通知、事件流标识、游标及合并并发请求的 Promise 仍是进程内状态。插话请求的去重持久化，重启后不会恢复已撤销条目，也不会重送已接收条目。

`document-references.json` 是独立的单文件派生索引：顶层包含 `schemaVersion: 1` 和按不带格式扩展名的文档身份组织的 `documents`；每项保存业务原值、独立 `computed` 配置与类型定义的指纹、直接引用及允许的目标类型。创建房间时，以及声明关系或节点变化时保存，不保存计算结果或运行时缓存。普通属性变化时只更新内存指纹，等到下一次保存索引时合并写入；重启后按原始文档核验并修复过期条目，反向引用从直接关系恢复。该索引缺失或 JSON 损坏可从原始文档重建；已有目录、符号链接或特殊文件拒绝覆盖。

读取文档时合并 `module/` 与 `game/`，再计算派生字段。角色已有的正文和属性不重复保存到选角索引；游戏文档修订号和界面刷新版本只在当前进程维护，不是持久存档字段。

创建房间先复制到 staging，再将元配置、字段定义、布局及游戏文档编译为 JSON。Markdown 的 frontmatter 合入字段对象，原正文保存为 `body`；业务原值和 `computed` 公式保留，计算结果不进入副本。原模组文件不修改，阅读页、图片等附件按原路径复制。转换目标已被其他文件或目录占用时创建失败，staging 整体清理；完成编译、校验和初始化后才发布房间。

文档标识由目录、名称和类型组成，不含最后的 `.json/.toml/.md`。读写和引用入口按标识解析唯一实际路径，输入中的格式扩展名只作为别名；响应、角色索引、版本及缓存使用规范实际路径。同名多格式文件直接报错，指定完整路径也不建立优先级。目录、字段定义配置和附件仍按实际路径访问。

`adventure.json` 只支持标准 JSON，顶层为 `room`、`notes`、`launch`、`party` 与 `contextSubscriptions` 分组，不接受其他顶层字段：

- `room` 保存房间资料、状态和时间；`room.id` 必须与目录名一致。
- `notes` 以稳定玩家 ID 为键保存纯文本笔记。
- `contextSubscriptions` 以主持 `host` 或队友身份 ID 为键，保存文档定位与 JSON Pointer 字段清单，缺省为空；不保存字段值，关闭订阅时保留清单。
- `launch.state` 保存本局开局阶段，未配置开局时为 `null`；`players` 保存各玩家的流程进度，`replacements` 保存角色更换请求与恢复所需的原进度。
- `party.characters` 保存角色身份、类型、归属、退场标记和文档路径。已落盘的角色不保存名称、正文、属性或运行时版本；新建角色在文档发布前以 `sourcePath: null` 和 `draft` 保存待落盘内容，文档发布后替换为路径索引。
- `party.companions` 保存队友席位：`empty` 只有 ID，`reserved` 另外记录所选角色，`active` 记录角色和加入时的聊天序号。席位 ID 同时是队友的虚拟玩家 ID，不在内部重复保存。队友的 `model`、`initiative`、文档查阅开关 `documentAccess`、个人声音覆盖 `voice` 与新增时复制的声音兜底 `defaultVoice` 直接保存在已入队席位中，随队友一起保存和删除；模型与声音为 `null` 时分别继承房间模型和模组声音，主动性缺省为自然，文档查阅缺省为关闭。提示词从冻结模组读取。

权威存档字段在存储边界通过 Zod 校验，缺少开局阶段、玩家进度、角色草稿或席位必要字段均拒绝读取；模组引用、角色可选性等动态约束仍由业务入口校验。权威文件必须存在且为普通文件，拒绝符号链接；不补造缺失文件，也不以默认空状态覆盖损坏存档。无法读取的冒险在列表中跳过并保留原文件，直接打开时报告错误。

`packages/core/src/node/sessions/room-storage.ts` 负责冒险状态的初始化、校验和同步读改写。`adventure-state.ts` 在业务事务期间共同暂存 `launch` 和 `party`，提交时只替换这两组，保留期间已保存的资料和笔记。角色文档中的刷新版本只在当前进程维护。

`settings.json` 由 `room-settings.ts` 独立校验和保存，包含房间级的 `chat`、`display`、`ai`、`hostSystemPrompt`、`compaction`、`tts`、`companion`、`companionRoleplayPrompt` 和 `contextSubscriptionsEnabled`；`companion` 是新增队友模板，个人配置仍保存在队友席位。连续点名响应上限为 `chat.mentionReplyLimit`，新对话链读取创建时的上限快照；聊天提交方式为 `chat.submissionMode`，值为 `auto` 或 `manual`，应用内置默认值为 `auto`。房间元数据 `chat.submissionModeRevision` 必须存在，创建时为 0，只有模式变化时递增，与模式在同一次文件替换中保存，其他设置更新保留版本；该元数据不属于应用默认设置。主持插话开关为 `chat.steeringEnabled`，缺省为 `false`。设置不保存凭据。主持指令与队友通用扮演指导 `companionRoleplayPrompt` 保存实际正文；语音 `config` 保存供应商引用、模型、音色与风格，`automatic` 是本局自动朗读开关。创建时从应用 `game.defaults` 复制，后续应用修改与内置提示词升级均不改变该快照。主持守则与表达要求统一属于 `hostSystemPrompt` 正文，不另存或注入固定守则区块，见[游戏聊天与 AI 实现](游戏聊天与AI实现.md)。

玩家消息正文为 `text` 字符串，队友正文为 Pi 公开工具中的 `text` / `intent` 字符串，均可承载 Markdown。玩家、主持、NPC 及队友的点名统一从正文身份链接解析。消息的可选 `mentions` 保存主机确认的 `{ id, label }` 目标与名称快照；省略或空数组表示没有点名。`replyToMessageId` 关联触发消息，等待响应使用 `queued` 状态。协议与调度约定见[游戏聊天与 AI 实现](游戏聊天与AI实现.md#主持运行与正文协议)。

两份文件独立读写：设置缺失或损坏只阻止依赖设置的操作，不妨碍读取冒险列表、资料和笔记；状态损坏也不阻止修正设置。已有文件损坏时保留原文，并拒绝保存补丁，不自动重置。创建房间在 staging 目录分别初始化两份文件后整体发布。设置空值规则见[配置存储](模组加载与文档实现.md#应用配置与房间设置)。

## SQLite 连接与迁移

`SessionDatabase` 使用内置 `bun:sqlite` 持有同步连接，Kysely 提供类型化查询构建与迁移管理。业务查询通过编译后的 SQL 和绑定参数同步执行，保持聊天事务内原有的提交顺序；事务成功后才发布通知。JSON 字段查询使用固定路径，以匹配表达式索引。

创建和打开房间时先完成迁移，再向业务层提供连接。迁移位于 `packages/core/src/node/storage/migrations/`，通过代码显式注册，便于桌面打包；同一进程对同一文件的并发打开共用迁移任务，已执行的迁移不重复应用。需要应用迁移时，结构变更与迁移记录在同一个 SQLite 写事务中提交，失败全部回滚。

驱动连接默认等待锁至多 5 秒；打开已有房间使用 `fileMustExist`，保留数据库、辅助文件和目录路径检查，不自动创建缺失存档。连接由调用方同步关闭，`SessionDatabase.onClose` 在连接关闭后执行全部资源释放回调，重复关闭无副作用。房间共享资源由 `sessions/room-resources.ts` 统一登记，打开失败也经过同一释放路径。

## 本局覆盖格式

基础模组里的文档被修改时，`game/` 同路径 JSON 文件保存字段覆盖数据：

```json
{
  "$overlay": 1,
  "values": { "hp": 6, "bag": [] },
  "removed": ["/note"]
}
```

- `values` 只保存相对基础文档发生变化的字段。对象递归合并，数组整体覆盖，包括空数组；普通 `null` 不表示删除，仍需符合类型约束。
- `removed` 使用 JSON Pointer 表示删除字段。删除与撤销覆盖不同：删除标记屏蔽基础字段，移除覆盖值和对应删除标记才恢复继承。
- 修改与读取覆盖都按类型定义检查 `mutable`。父对象不可写时，允许覆盖明确可写的子字段。数组不可整体写入时，只允许其中可写子字段发生变化；改变只读身份或顺序会报错。
- 正文以获准修改的 `body` 字段保存差异；未覆盖正文时从 `module/` 继承。正文更新仍受 Schema 的 `mutable` 约束。
- 本局新增文档统一保存完整 JSON 内容；输入路径可省略扩展名或带三种格式扩展名，实际落盘固定为 `.json`。不能通过其他格式别名重复创建已有文档；基础文档被删除后，遗留覆盖会报错，避免把补丁误当成完整文档。
- 角色、状态、资料展示及 AI 的 read/find/grep 使用同一合并视图。文档图片优先使用 `game/` 附件，缺失时使用 `module/`；模组封面和主持头像只读取冻结的 `module/`。
- 写入使用房间锁及临时文件重命名；与基础值相同的字段不保存差异，恢复为跟随基础模组。

房间基础模组副本的文件默认设为只读，游戏更新工具只写 `game/`。桌面提供手动检查和同步来源模组的入口，运行协调与候选校验见[模组同步实现](模组加载与文档实现.md#已有冒险的模组同步)。未覆盖字段采用新基础值，已有覆盖继续优先；不兼容的字段类型、引用、权限或已保存流程变更拒绝同步。数组被整体覆盖后，其中未改过的元素也不再单独继承基础更新。

文档顶层 `computed` 保存当前文档的公式覆盖，随 `module/` 基础文档或本局新增文档保存。已有文档的公式配置只从基础副本继承，`update` 不开放配置区的修改权限；计算结果不落盘。内部原始快照将公式配置与业务 `values` 分开，累计覆盖在文档头部保留配置供渲染进程求值；计算展示模型不携带配置。文件格式保持顶层 `computed`，读写边界负责拆分和合并。嵌套字段通过字段路径定位，具体有效 Schema 与权限边界见[模组加载与文档实现](模组加载与文档实现.md#计算与展示契约)。

物品实例使用持有者文档内的原始对象列表，不增加独立存档文件。引用定义的顶层 instance 配置随冻结文档保存；实例 state 只保存显式原值，计算结果不进入基础副本或本局覆盖。原始快照保留定义配置供服务端与渲染进程求值，玩家字段投影移除内部配置及主持状态。

计算器为已解析的实例条目生成只用于投影的 $instance 标记，包含公开状态与有序摘要；玩家只保留公开状态和摘要。绑定行的源数据校验拒绝该标记，写入接口也拒绝实例计算字段，不能把展示结果作为原始状态保存。普通更新与批量 Patch 先按实际引用展开字段权限，再校验整份实例状态；整体替换同样检查已有实例的只读状态。

实例中的声明引用加入直接依赖索引。实例绑定文档的引用关系按当前定义重新核对，定义变化后不复用仅凭持有者指纹匹配的旧关系；恢复时从定义与原始 state 重建，不执行资源扣减或默认初始化。房间协议与引用索引版本保持 1，不提供旧开发格式迁移。

## 写入与恢复边界

`sessions/game-state.ts` 是游戏文档的业务入口，内部由 `game-document-source.ts` 负责原始文档与引用读取，`game-document-views.ts` 管理计算和公开投影，`game-document-read.ts` 组织工具读取，`game-document-write.ts` 协调校验、暂存与发布；游戏文档可写性检查与明确结束操作位于 `adventure-status.ts`。提交由同一入口协调，统一管理房间锁和部分成功的处理。

游戏文档按规范相对路径定位，类型由一级目录与 `module/.types/` 定义决定，嵌套子目录只承担资料分组。更新在房间锁内读取最新合并内容，校验字段权限、引用、计算结果和容量后，先暂存文档及变化后的单 JSON 引用索引，再依次发布文档和索引，推进当前进程的版本并通知界面。`batch_update` 先按整批最终候选校验，全部文档与合并引用索引暂存完成后才按请求顺序发布；发布前取消清理暂存，开始发布后继续完成，不因取消主动中断。任一暂存失败不发布文档；发布失败清理尚未发布的临时文件，报告已保存和未保存路径。部分文档或全部文档已发布但索引发布失败时，丢弃内存快照，已发布文档共同推进版本，下次读取按当前文件修复索引；角色索引同步失败同样报告文档已保存。进程中断造成文件不一致时，在下次初始化按指纹修复引用索引，不回滚原始文档。图片与工具各自校验真实路径，不允许读取副本之外的文件。

冒险状态和设置 JSON 各自在当前进程同步读改写，并通过同目录临时文件替换；涉及聊天的组合操作使用 SQLite 写事务，但不构成跨文件事务。没有游戏操作日志；取消不会撤销已提交变化，跨文件部分成功时须从已保存事实继续。聊天消息使用 SQLite 事务，触发消息和全部点名回应共同提交，通知在事务中暂存，成功提交并登记排队任务后才发布到内存缓存和广播；房间文件与 SQLite 之间不保证崩溃恢复事务。通用文件队列、原子替换和跨进程限制见[文件存储](文件存储.md)。

模组同步在 `game/` 锁中构建 `.module-sync/candidate/`，仅在候选完全校验通过后发布。候选包含新模组和当前游戏覆盖的临时副本；权威 `game/`、设置、聊天数据库及 Agent 历史不替换。发布前备份原 `adventure.json` 和可选引用索引，写入 `prepared` 恢复标记，再同步替换基础模组、保留当前资料与笔记的新冒险索引和新引用索引，最后将标记改为 `committed`。发布失败恢复旧模组和关联文件；恢复失败保留标记与备份。下次读取房间时在同一工作区锁内恢复：`prepared` 回退原版本，`committed` 保留新版本并清理备份。没有标记的候选属于未发布临时资料，下次同步可清理。该恢复机制处理发布过程中断，不提供不同开发版本的迁移，也不保证机器掉电时文件系统的持久写入顺序。

角色归属和建卡恢复见[角色与开局实现](角色与开局实现.md)，笔记自动保存见[房间笔记](游戏聊天与AI实现.md#房间笔记)，运行时覆盖传输与进程内版本见[房间增量同步](房间增量同步实现.md)。

聊天消息通过 Pi 原生会话与条目引用关联完整历史，开场消息直接引用聊天消息 ID；当前运行通过房间投影的 `sections.chatActivity` 暴露稳定 `runId` 和当前消息 ID，插话分段不会改变运行身份。该投影与最早排队消息均从当前房间事实生成，不是额外存档或历史分页结果。Pi 与 SQLite 的边界恢复见[游戏聊天与 AI 实现](游戏聊天与AI实现.md#增量与恢复)。

普通主持输入的交接批次保存在内部 `chat_input_batches` 表，包含来源、提交快照与接收状态；公开消息的 `inputBatch` 只保存标识与接收状态。领取、接收和放弃分别记录，原生 Pi 消息的 `details` 保存对应接收标记。跨存储对账及未送达输入的处理见[普通主持输入交接](游戏聊天与AI实现.md#普通主持输入交接)。
