# 发布流程

## 工作流

| 入口                                    | 触发条件                   | 行为                                            |
| --------------------------------------- | -------------------------- | ----------------------------------------------- |
| `.github/workflows/ci.yml`              | PR、手动运行、发布流程调用 | 格式、类型、完整测试与构建；PR 另验收桌面安装包 |
| `.github/workflows/release-desktop.yml` | `desktop-v*` tag           | 检查 → 各平台打包与验收 → Release 草稿          |
| `.github/workflows/release-cli.yml`     | `cli-v*` tag               | 检查 → CLI 打包与验收 → npm 发布                |

发布工作流复用 CI，共用 `.github/actions/setup/action.yml` 安装根级 `packageManager` 指定的 Bun。依赖统一从根目录按 `bun.lock` 安装；共享包随产品构建，官网和剧情模组不参与构建。CLI 兼容性检查与 CLI 发布流程另外安装 Node.js 22.12.0，验证支持的最低版本。第三方 Actions 固定到提交 SHA，升级时同步核对版本。

开发环境安装步骤缓存 Bun 的依赖下载目录，以及 Hutch 下的 `npm/`、`releases/`、`toolchains/`；按操作系统、架构、锁文件与工具链配置区分缓存。命中后仍执行 `bun install --frozen-lockfile`、构建和验收，下载缓存不包含 `node_modules`、项目构建目录、安装包或签名凭据。缓存不可用时按正常流程重新下载。

根级 `bun run typecheck` 和 `bun run build` 由 Turborepo 调度。类型检查、CLI 构建以及桌面 Vite 页面构建可复用成功任务的结果；共享包源码通过依赖任务参与指纹，实际 Bun 版本、操作系统、架构和构建环境变量也参与区分。CLI 打包与测试准备复用同一构建任务。桌面主进程及原生应用始终重新构建，完整测试、打包、签名、公证、分发验收和 npm 发布均实际执行，不以缓存命中替代。

Actions 在开发环境安装步骤恢复并保存 `.turbo/cache`，按系统和架构隔离归档，无需新增 Secret 或远程缓存账号。缓存键包含锁文件、任务配置、提交和 job，后续提交通过前缀恢复已有任务结果，再由 Turbo 决定哪些任务需要重跑。`scripts/tasks.ts` 统一注入实际平台和 Bun 版本；排查时可运行 `bun scripts/tasks.ts run typecheck --force` 强制执行，或用 `--dry=json` 查看依赖和指纹。缓存输出不包括签名凭据、桌面原生应用及已发布的安装包。

GitHub 缓存有分支和 tag 作用域限制，PR 保存的缓存不能由合并后的发布 tag 直接读取；首次发布或新的 tag 可能需要重新下载，同一 tag 重跑可复用已有缓存。默认分支已有的兼容缓存也可供其他分支及发布流程读取。

普通分支 push 不触发检查；创建或更新 PR 时执行仓库检查，通过后调用 `.github/workflows/build-desktop.yml`，构建并验收 Windows x64、Linux x64 和 macOS ARM64 安装包。PR 不传入签名凭据、不创建 Release；安装包作为 Actions 产物保留 14 天。桌面发布复用同一构建与验收流程，并按配置签名、公证；手动运行仓库检查只执行格式、类型、测试与构建。CLI 分发包验收仍在 CLI 发布流程执行。`scripts/release/smoke.ts` 使用独立临时模组与配置，验证分发产物的版本、帮助、模组加载、原生公式计算和退出码。CLI 从 tgz 独立安装后分别使用 Node.js 和 Bun 运行，使用符合类型目录结构的测试资料覆盖 JSON、TOML 与 Markdown 解析，并检查已安装运行依赖的许可文件；桌面则运行各平台打包后的应用，并验证包内 SQLite 驱动与 Kysely 的加载、写入、事务回滚和重开恢复。

## 发布版本

1. 修改目标产品的 `package.json` 版本：桌面为 `apps/desktop/`，CLI 为 `packages/module-cli/`。
2. 从根目录运行 `bun install` 更新根级锁文件，提交 PR，确认检查和桌面分发验收通过后合入默认分支。影响公开行为或模组格式时同步修改官网正文。
3. 从该提交创建并推送对应 tag，版本必须与目标包完全一致：

```sh
# 桌面版本
git tag -a desktop-v0.1.0 -m "发布桌面版本 0.1.0"
git push origin desktop-v0.1.0

# CLI 版本
git tag -a cli-v0.1.0 -m "发布 CLI 版本 0.1.0"
git push origin cli-v0.1.0
```

两种产品独立发布；例如 `desktop-v0.2.0-beta.1` 会创建预发布草稿，`cli-v0.2.0-beta.1` 则发布到 npm 的 `next` 标签，不创建 GitHub Release。发布时重新检查 tag 对应的提交，不临时改写版本。

## 桌面产物与签名

| runner         | 架构  | 产物                               |
| -------------- | ----- | ---------------------------------- |
| `windows-2022` | x64   | ZIP 安装包（setup 与相邻 payload） |
| `ubuntu-24.04` | x64   | tar.gz 安装包                      |
| `macos-15`     | ARM64 | DMG                                |

各平台构建另生成 `.tar.zst` 更新归档（macOS 为 `.app.tar.zst`）与对应通道的更新元数据；更新归档用于分发验收。更新归档、元数据和可选的 `.patch` 差分补丁均以框架原始文件名上传 GitHub Release，供后续接入自动更新使用。Electrobun 2.0.4 官方未发布 macOS x64 core，当前不生成 Intel Mac 安装包。Linux 目标机需要 WebKitGTK 4.1、GTK 3、Ayatana AppIndicator 和 librsvg；Windows 使用 WebView2。

`electrobun.config.ts` 和 `hutch.config.ts` 固定框架与 Bun 主进程。开发输出在 `out/desktop/dev-<os>-<arch>/`，稳定输出在 `out/desktop/stable-<os>-<arch>/`，附件位于 `release/`。稳定应用外层是自解压安装器，验收程序从更新归档解出真实应用，使用包内 Bun 运行包内 CLI 和 smoke 程序。不得只使用开发机器的 Bun 或从开发目录加载依赖。

SQLite 使用内置 `bun:sqlite`，Kysely 通过共享适配器同步访问；不分发 `better-sqlite3`。QuickJS Wasm 及其运行依赖作为外部文件复制，其他依赖参与打包。SQLite 验收覆盖加载、写入、事务回滚和重开恢复，Wasm 验收实际创建 QuickJS 上下文并执行代码。

macOS 签名使用仓库 Secrets `MAC_CSC_LINK`（HTTPS 证书地址或 Base64 P12）、`MAC_CSC_KEY_PASSWORD` 和 `MAC_DEVELOPER_ID`（完整 Developer ID Application 标识）。CI 在临时钥匙串导入证书；`MAC_DEVELOPER_ID` 配置后开启签名。公证使用 `APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD`、`APPLE_TEAM_ID`，映射到 Electrobun 的对应环境变量。未配置时生成本地验收包。Hutch 当前不自动签署 Windows 安装器，正式发布前按目标环境补充签名。

本机从根目录运行 `bun run dist` 后执行 `bun scripts/release/smoke.ts desktop` 验收稳定包；开发包可使用 `TARP_SMOKE_CHANNEL=dev`。最后一个任务上传以下附件，不自动公开 Release：

- `TARP-<版本>-windows-x64-setup.zip`
- `TARP-<版本>-macos-arm64.dmg`
- `TARP-<版本>-linux-x64-setup.tar.gz`
- `stable-<系统>-<架构>-TARP.tar.zst`（macOS 为 `TARP.app.tar.zst`）
- `stable-<系统>-<架构>-update.json`
- `stable-<系统>-<架构>-<hash>.patch`（构建生成时上传）
- `SHA256SUMS.txt`（校验全部安装包和更新文件）

安装包在汇总时重命名，构建与验收仍使用框架原始文件名。桌面 Release 不额外上传源码包，使用 GitHub 按发布 tag 提供的源码归档；新建草稿的版本说明附上对应源码链接。发布 tag 必须保留，源码归档应包含构建所需的项目源码、脚本和根级锁文件。

## 验收与公开

流程完成后，在 GitHub Releases 检查草稿附件、版本说明和源码。在目标系统验收安装、GUI 启动、模组加载、计算及签名，再公开草稿；自动化验收不能替代安装器和 GUI 验证。源码与许可声明随分发产物提供，公开后同步官网的玩家下载入口。

## CLI 自动发布到 npm

推送 `cli-v*` tag 后，工作流先检查版本、打包并在 Node.js 与 Bun 下独立安装验收，再将同一份 `packages/module-cli/out/tarp-module-cli.tgz` 直接发布到 npm，不创建 GitHub Release，也不生成额外源码包或校验附件。包名为 `@jointarp/module-cli`，公开访问；正式版本使用 `latest`，带预发布标识的版本使用 `next`。npm 包会在流程成功后立即公开。CLI 工作流仅需仓库内容读取权限，发布使用 `NPM_TOKEN`；保留对应 `cli-v*` tag 作为版本源码入口。

首次使用前完成以下配置：

1. npm 账号拥有 `@jointarp` scope，并有权发布 `@jointarp/module-cli`；首次发布时 Token 的权限需要覆盖新包创建。
2. 在 npm 创建 Granular Access Token，授予目标包或 scope 的发布写权限；启用用于无人值守发布的 2FA bypass，并设置合适的有效期。
3. 在 GitHub 仓库 `Settings → Secrets and variables → Actions` 添加 `NPM_TOKEN`。工作流仅在凭据检查和发布步骤读取它，不将其写入下载缓存。
4. 修改 CLI 版本并同步根级锁文件，合并 PR 后推送完全一致的 tag。发布成功后可用 `bunx --bun @jointarp/module-cli@0.1.0 --version` 验证目标版本。

工作流使用 Bun 发布，无需 npm CLI。缺失 Token、权限不足、Token 过期或同版本已存在均会使任务失败；不会跳过失败并宣称已发布。

构建或上传失败可重跑失败任务，Actions 中间产物保留 14 天。已有草稿可重跑更新同名附件，已公开版本拒绝覆盖；修复源码或产物时发布新版本，不移动已发布 tag。npm 同名同版本不可重复上传。
