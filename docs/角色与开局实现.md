# 角色与开局实现

开局与建卡配置、任务参数和示例统一维护在官网：「开局方案」、「阶段式建卡」。本文维护服务端进度、身份、持久化和恢复契约。

## 进度与身份

真人玩家、AI 队友席位及角色的新 ID 统一使用 16 位 Nano ID，包含大小写字母、数字、`_` 和 `-`，身份比较区分大小写。共享校验只约束为非空 URL 安全字符串，不依赖 UUID 格式或固定长度；生成入口负责长度。房间内新增角色和队友席位时排除已有身份，点名、掷骰与开局 RPC 共用此约束。房间、消息、运行及事件流 ID 使用 UUID；房间协议版本保持 `1`。

`packages/core/src/shared/launch.ts` 定义客户端契约，`packages/core/src/node/sessions/launch-store.ts`、`launch-db.ts` 维护开局和玩家进度。开局从房间冻结模组读取；不根据文档名称推断角色用途。序章回答仅供流程恢复，不作为角色属性或主持指令；建卡由 `creationFlow.workbench` 显式执行。

准备名单保存在工具消息中，当前已在房间的玩家确认后启动讲述，后来加入者不阻塞进度。一个开局时直接选定，不生成选择卡；多个开局先写简介消息，再插入真实开局工具卡。选角、组队卡同样由服务端写入 `chat_messages` 并经订阅推送，客户端不能按进度在时间线末尾补造。

真人与 AI 共用角色占用校验。选中 ID 直接保存在玩家进度或队友席位，不另建预留表；取消、换选释放，确认后绑定，每个玩家在本房间只绑定一个角色。首次确认锁定房间开局；锁定前切换开局清除受影响的未确认建卡进度。退场或接管由主持工具发起，保留旧角色记录，不重播开场。

首次确认玩家决定开局组队；可用 AI 预设角色存在时进入组队工具卡，否则直接开场。其他玩家确认不重复触发组队。组队提示、选择、席位均持久化，确认后才以实际小队初始化开场，队友公开记忆从正式开场开始。

## 建卡执行与保密

共享求值位于 `packages/module/src/schema/creation-workbench.ts`。工作台不依赖模型，界面与服务端使用同一冻结定义，服务端保存原生 JSON 输入、引用选择和随机记录；拒绝过期版本并按请求 ID 去重。生成只补缺失骰值，返回浏览或重启不重掷；切换文档分支只结算当前分支，同时保留随机历史。

任务绑定沿角色 Schema 校验，不允许写计算字段；运行时 `mutable` 不限制初始建卡赋值。输入对象只接受已声明字段，派生值由计算核心生成。参考文档中的任务列表必须是 GM 字段，公开任务配置拒绝加载。私密任务、来源与目标必须保持对应权限；仅所属玩家工作台获得任务值与进度，不能借公共对象或其他玩家进度泄露子字段。

核对与确认均在服务端重新求值，不信任客户端传来的最终卡片；不解析 Markdown 表格或规则正文生成属性。确认后草稿不继续充当第二份可修改状态。随机表、采购、字段互换使用同一求值入口；具体货币、护甲、背包和规则仍由模组定义。

## 开场消息与恢复

序章介绍、开局方案简介及预写 beat 共用叙事标签解析器，每个说话人分段保存一条独立 `scripted` 消息。没有标签的正文作为旁白，正文空行不拆消息；NPC 文档标识与可选公开称呼分别保存为 `speakerPath` 和 `nickname`，按来源及分段序号生成稳定 `postKey` 去重，不伪造模型或用量。即时讲述由服务端每 60 毫秒追加最多 8 个 Unicode 字符，使用同一条消息的版本更新推送并保存当前正文；状态由 `running` 转为 `complete` 后才推进讲述索引，完整输出后短暂停顿再发送下一段或流程卡。客户端统一按消息状态平滑刷新，不额外逐字播放。重开时沿用已保存的消息 ID 和正文前缀继续未完成的输出，已完成消息直接展开，不重播；讲述间隔不能参与业务去重。初始化确认不写成公开旁白。

预写开场先初始化再发布文本；没有额外初始化指令时不需要模型。AI 开场在一次主持运行中初始化并流式叙事。每批预写正文与消息状态在 SQLite 事务内保存；全部正文输出完成后才提交开场完成标记，文件变更不属于聊天事务。已提交角色或世界变化不因停止叙事回滚，开场恢复从当前文件事实继续并创建新 Pi 回合；初始化指令不追加到后续每轮。

有额外初始化指令的预写开场，初始化消息成功保存为 `complete` 后，仍保持开场状态为 `running`。`ChatRuns` 在收尾中释放运行占用，再调用 `kickNarration()` 自动播放预写正文；播放检查会拒绝仍有 AI 运行占用的房间，因此不能只在释放前触发。打开房间或同步开局状态也会检查并恢复未完成的预写播放，正常接续不依赖这些恢复入口。

配置了开局流程时，行动要求角色确认和开场完成，开场期间普通聊天不阻塞；未配置开局流程时不执行这一检查。平台不初始化场景或检查入场；一次性状态初始化由模组开局指令明确说明，位置和参与情况由模组规则解释，见[游戏状态实现](游戏状态实现.md)。

## 存档结构

开局配置从房间的只读 `module/` 副本读取。`adventure.json.launch` 保存房间开局状态、玩家进度、建卡草稿和骰值；`party` 保存角色 ID 与归属、退场标记和 AI 队友席位。已有角色的正文和属性从 `module/` 与 `game/` 的合并视图读取；新建角色确认后先在 `adventure.json.party.characters` 保存待落盘草稿，随后落为 `game/<角色类型 ID>/<角色 ID>.json` 并替换为路径索引；不持久保存角色展示字段或刷新版本。

`session.sqlite` 保存完整聊天消息并支持历史分页；公开事件和恢复游标在当前进程内维护。界面刷新计数也在当前进程内维护；`chat_messages` 保存序章、开场旁白及开局、选角工具卡。

序章、开场和工具卡都写在 `chat_messages` 里。待处理的决定以尚未完成的工具卡为准。建卡流程随 `module/` 快照冻结，角色原始内容以房间文档合并视图为准，格式见[存档格式](游戏房间存档格式.md)。AI 使用统一的 `read`、`update` 读取和修改角色，计算字段不落盘。

`preludeFlow.steps` 只负责序章叙事和问答，不写入角色卡。角色创建必须使用 `creationFlow.workbench`。

没有角色用途标记的文档不会仅凭名称被识别为角色。

## 验证

测试覆盖序章分支、字段保护、进度恢复、骰子重放、批量生成幂等、角色唯一性、无模型开场、初始化失败重试，以及序章和工具卡幂等写入。修改持久化或协议时运行 `bun run test`、`bun run typecheck`、`bun run build`；执行范围见[测试维护](测试维护.md)。
