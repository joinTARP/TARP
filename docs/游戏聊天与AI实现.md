# 游戏聊天与 AI 实现

模型连接、行动提交、队友、掷骰和笔记的玩家说明统一维护在官网文档。本文维护业务协议、生成调度、恢复、凭据及进程通信边界。

## 代码职责

### 服务入口与模块依赖

`packages/core/src/node/game/chat-service.ts` 是稳定的对外入口，负责组合服务、房间连接、恢复和关闭。内部实现集中在 `packages/core/src/node/game/chat/`；业务模块仅接收 `types.ts` 中所需的共享能力，以及明确声明的下层依赖。

| 内部模块             | 职责                                           |
| -------------------- | ---------------------------------------------- |
| `store.ts`           | 聊天表结构、事务、消息版本、历史和增量事件读取 |
| `activity.ts`        | 在线玩家、多订阅计数、运行与配置互斥、关闭等待 |
| `input-batches.ts`   | 普通主持输入批次、接收确认与恢复对账           |
| `turn-queue.ts`      | 提交模式、待处理行动、消费队列和主持输入       |
| `mention-queue.ts`   | 点名回应排队、真人优先级、接续上限与队列取消   |
| `steering.ts`        | 持久插话队列、容量权限、批次接收与恢复对账     |
| `launch-cards.ts`    | 准备、开局与角色流程在聊天中的卡片投影         |
| `narration.ts`       | 预写旁白、开场完成、播放节奏及任务清理         |
| `runs.ts`            | AI 回合执行、结果收束、主持裁定及队友接续      |
| `run-events.ts`      | 公开增量缓冲与批量持久化                       |
| `run-diagnostics.ts` | 运行详情、历史与指标缓存                       |
| `submissions.ts`     | 玩家发送、请求幂等及手动继续入口               |
| `launch.ts`          | 开局操作、恢复及流程编排                       |
| `companions.ts`      | 队友席位、角色控制权与个人设置                 |
| `dice.ts`            | 权威掷骰、重复请求、超时结算及主持等待         |
| `sync.ts`            | 玩家投影、订阅、流控确认与订阅清理             |

提交入口依赖执行模块，双方共同读取下层队列；开局入口依赖执行与旁白，三者共同使用卡片投影。执行模块不回调提交入口或开局入口，旁白不回调开局入口。卡片投影和普通行动队列不自行启动 AI；房主显式提交插话时，插话服务负责停止当前运行并启动新运行。写入和状态推进由调用方划定事务边界。

`RoomState` 仅共享数据库、变更通知与关闭标记。旁白任务和计时器由旁白模块管理，掷骰计时器由掷骰模块管理，投影缓存由同步模块管理，运行详情和指标由诊断模块管理；各模块以房间连接为弱引用键隔离缓存。关闭时先标记房间不可用，终止订阅、旁白等待和 AI 运行，等待配置与指标任务完成，再清理计时器并关闭数据库。

### 渲染端与连接状态

渲染端的 `features/sessions/ChatPanel.tsx` 组合角色上下文、聊天列表和输入区域。`ChatMessageEntry.tsx` 负责消息正文、头像和流式呈现；`ChatComposer.tsx` 消费 `use-chat-composer.ts` 提供的草稿、重试和提交操作。玩家资料读取和昵称更新由 `use-player-profile.ts` 管理。

输入区最右侧用同一个固定尺寸按钮执行发送或停止；房主运行 AI 时显示方形停止图标，结束后恢复发送箭头，切换不卸载按钮。生成期间允许的插话、聊天和队友发言通过停止按钮左侧的发送入口提交；停止请求进行中禁用重复操作并保留草稿。

对于尚未确认成功的发送请求，按正文（含身份链接）和原输入模式匹配恢复的草稿。匹配时，Enter 和重试按钮优先复用原 `clientMessageId`，不因主持已经开始运行而转成新的插话请求；输入区同步显示重试用途。正文或点名链接发生变化的新草稿仍按当前用途发送，重试旧请求不会清空新草稿。

`room-connection.ts` 保留单一房间通知流，并将聊天状态委托给 `room-chat-store.ts`。消息、提交模式、待处理集合和历史分页统一由该存储合并通知、请求响应及历史快照；合并时按消息版本判断新旧，避免旧内容覆盖新内容；待处理标记以合并后的消息版本为准。重复或较旧的消息通知、未变化的提交模式不发布新快照。多个面板共享分页请求和分页边界。

`use-chat-log.ts` 通过 `useSyncExternalStore` 订阅聊天及连接快照，仅维护未读、分页反馈和朗读等视图状态。输入 Hook 通过接收消息、确认提交模式、报告错误等明确操作更新日志，不接收 React 原始状态 setter。房间传输使用注入的 `GameClient`，桌面模型配置读取由面板传入具名函数。切换房间时以房间 ID 为组件 key，重置订阅和输入状态，并取消面板请求。

模块划分以实际职责和调用关系为依据。共享的房间瞬态状态集中在活动模块；独立存储、异步任务及恢复逻辑保留各自边界。单一能力使用具名函数传递，新增抽象需有当前代码中的实际复用或隔离需求。

## 主持运行与正文协议

### 运行入口与主持指令

Pi 驱动主持运行；本机游戏路由通过 oRPC MessagePort / Electrobun 原生桥连接主进程，主机统一排序与持久化。普通无点名聊天不触发 AI 运行，在队友后续调用时按入队时间进入其公开上下文；合法点名聊天进入队友公开上下文并定向唤起接收者。点名主持的聊天单独排队，由主持作场外回应；聊天均不作为行动裁定。行动由当前自动 / 手动提交方式决定是否触发运行，玩家身份与角色归属按认证上下文解析。

普通行动以实际保存消息前的最新提交模式为准；模型凭据读取及等待队友结束之后都重新核对模式。准备期间切到手动提交时保存为待提交，不启动主持，也不会因读取此时已不需要的主持凭据失败而拒绝保存；切到自动提交时先取得可用凭据，再核对模式及运行状态。已经提交的请求重试只读取原结果，不按新模式重新执行。

`shared/mentions.ts` 为玩家、主持旁白、NPC 发言及 AI 队友提供统一的身份链接解析。发送接口仅传 Markdown 正文；队友聊天与行动工具仅传 `text` / `intent`，不接收独立点名参数。完整的 `[@名称](#mention/身份ID)` 链接声明目标，Markdown 解析跳过代码、引用和图片，普通 `@名字` 不触发。主机按当前公开候选校验、去重，并在消息的 `mentions: [{ id, label }]` 中保存稳定 ID 与接收时名称；链接文字不参与身份匹配。分类与调度使用主机确认的字段，不保存文字偏移。

系统提示每轮读取冒险保存的通用主持指令正文，组合冻结模组指令、当前状态与资料目录。`packages/core/src/shared/host-system-prompt.ts` 的 `defaultHostSystemPrompt` 是主持守则与表达要求的唯一默认正文，按信息披露、行动裁定、NPC 扮演、节奏连续性、中文表达及排版检查组织。完整正文通过通用主持指令入口查看、修改、保存和恢复默认；创建冒险时保存正文快照，自定义正文整体替换默认内容。

主持行为与文风使用本局保存的正文。应用只另行注入工具与状态操作要求、玩家控制权、输入输出与点名交接协议及房间上下文。固定的 `hostMentionInstructions` 每轮加载，要求在确需澄清、选择、回答问题或交接发言时主动使用完整身份链接点名，问完等待；已明确的行动直接裁定，不机械轮流点名。主持取得统一的玩家与角色名单，不按真人或 AI 标注身份；固定提示词和工具说明只约定点名身份、检定目标与等待结果，不向模型解释响应生成、排队或点击方式。点名调度和掷骰等待方式由平台按控制类型处理。修改应用默认指令或升级内置正文不会覆盖已有冒险；旧冒险需要在本局编辑或恢复默认才能采用新正文。

固定主持协议要求裁定前核对状态、保存后再叙述结果，并遵守玩家控制权；位置、场景与同行关系由模组字段和规则解释。通用主持指令保持可编辑，固定工具与交接协议独立追加。开局背景原文进入独立系统板块，作为已发生背景，不代表当前位置，也不逐轮复制到玩家输入。每次调用提供本局资料入口及身份映射；队友名单只包含身份，已提交行动通过输入批次进入上下文。掷骰工具只要求指定玩家身份和等待真实结果，交互等待或立即结算由平台处理。

### 工具执行与正文解析

主持默认启用 Pi 原生 `codemode` 扩展，使用 `on` 模式保留直接工具调用，关闭脚本的 `models` 能力。脚本可整理资料、计算规则并调用现有受控工具；掷骰工具使用 Pi 的 `model-only` 暴露方式，只能直接调用。AI 不执行命令、加载全局或模组携带的 Pi 扩展，也不能修改类型与附件。队友不启用 `codemode`。更新权限与 Markdown 正文处理见[文档更新](模组加载与文档实现.md#文档更新与正文权限)。

脚本执行、取消、顺序调度及 `store/load` 均由 Pi 管理；辅助存储不作为游戏状态来源。关联的多文档更新优先调用 `batch_update`，统一校验后再发布；单文档 `update` 与批量工具共用受限 JSON Patch 执行与提交能力，创建使用 `write`。不同工具调用逐次提交，脚本失败不回滚已提交的变更；批量工具的文件发布失败也可能部分成功，下次裁定先核对当前状态，不能整批重试或重复结算。

`packages/module/src/schema/narrative.ts` 为 AI 回复和预写正文共用的解析器，`packages/core/src/shared/narrative.ts` 重导出解析能力并提供运行时协议。解析独占行的 `<message narrator>`、`<message npc path="…" name="…">` 和闭合标签，NPC 路径规范化为文档标识，公开称呼可省略。正文可在未闭合时流式展示；遇到下一个标记或回复结束时，也会结束当前分段。聊天的 `chat-markdown.ts` 在已有 Markdown 渲染树中兼容标准解析器未识别的中文双星号加粗，包括标记内侧空格和相邻中文标点；历史与流式显示共用，不改写存档或朗读正文。代码、转义及实体解码后的字面标记不重新解释，资料引用继续由现有引用插件处理。半截标记行暂存，原始文本和增量照常保存，历史、重连和中断共用解析；无标记正文作为主持旁白。

AI 和预写 NPC 发言均按角色文档标识关联；预写正文解析后将路径保存在 `speakerPath`。头像、默认名称和资料入口只使用按需读取的玩家公开投影；显式 `name` 作为本条消息的公开称呼，不参与身份匹配。优先 `avatar` 后 `image`，不能唯一定位或资料不可见时使用占位符。媒体地址在展示时解析，不写回文档。

玩家和队友头像使用原生按钮，点击直接打开角色卡，右键保留点名与查看角色卡菜单；NPC 头像复用文档引用入口打开详情，使用当前房间的公开投影与可见性校验，不按姓名或任意代号猜测文档路径。

`chat-timeline.ts` 在完整时间线上判断连续消息分组。同一说话人的连续预写消息从播放开始就合并头像与标题，正常完成不改变分组；NPC 切换还需核对 `speakerPath`，同名的不同人物保留独立头像。失败或中断消息保留独立标题和状态。

`use-frame-text.ts` 将挂载后收到的实时追加按约 40ms 的窗口合并，并在下一帧整批展示，不人为逐字拆开 Markdown 标记。持续接收不推迟当前窗口的刷新；正常完成时先显示完短缓冲中的内容，中断、取消、失败、正文替换及系统减少动态效果模式直接显示权威正文。历史和重新挂载的消息直接显示已有内容，不重播。聊天正文使用 Streamdown 分块缓存，生成及显示剩余缓冲内容期间由 Remend 处理未闭合语法；结束后关闭补全，保留相同分块渲染结构。复用中文加粗、资料引用、点名导航和本地图片组件，禁用原始 HTML，不修改原文、消息保存或语音队列。

`ChatMessageList.tsx` 由虚拟列表维护可见窗口、尺寸测量和前插历史的阅读锚点，底部追随统一使用按帧更新目标的滚动动画，避免尺寸补偿与动画同时移动视口。检定卡插入前后，主持正文按原生消息中的起始位置维持同一渲染键，续写尾段收束后不换键，保留正文节点和高度缓存。Markdown 链接渲染器保持组件类型稳定，导航回调通过上下文更新，不因角色映射变化重建资料链接。聊天正文中的资料引用首次取得可见名称后，在当前挂载期间保持该文字；等待重算、资料隐藏或失效时保留等宽样式的正文文字，暂停预览和详情入口，不用占位名称替换已显示称呼。此行为只作用于聊天文本，资料卡与字段展示继续遵守实时投影；不改动计算器、同步版本或查询缓存。首屏直接定位最新消息；实时输出和输入区尺寸变化平滑追随。向上滚动或开始触摸操作立即暂停追随，回到最新消息后恢复；减少动态效果模式直接定位。

## 主持聊天与消息用途

输入区使用「聊天 / 行动」表示用途，合法点名指定交流对象并将整条消息归为聊天。玩家与队友的行动消息在名称旁显示旗帜图标，悬停或键盘聚焦时说明用途；聊天消息不显示用途标记。队友消息不额外展示「AI 队友」身份标签，NPC 标签保留。连续玩家消息切换用途时不合并标题，待提交状态独立展示，作者可在自己的待提交玩家消息旁使用「改为聊天」。

`ChatMentionQueue` 同时调度队友与主持聊天，统一遵守事务保存、真人优先、连续响应上限、取消和重开不重放的规则。点名主持的消息及其回应均保存 `chatOnly=true`，回应关联 `replyToMessageId`；不进入待提交行动集合、不消费已有行动，也不使用主持行动批次。主持聊天使用当前主持模型和原生主持会话，输入正文明确记录场外用途，后续行动和记忆压缩继续区分讨论与已提交意图。

运行通过 `hostChat` 标记限定场外回应，仅注册 `read`、`find`、`grep` 和 `ls` 只读工具，关闭 `codemode`、写入、结束冒险、掷骰及插话接收。固定追加的 `hostChatInstructions` 要求只解释规则、澄清公开描述和沟通节奏，不扮演 NPC 或推进剧情，并继续遵守信息披露边界。主持聊天成功结束后，正文中经确认的身份链接点名继续唤起对应对象，沿用同一条点名链的响应上限；没有有效点名时不触发普通队友反应。同一条输入显式点名的其他对象仍各自排队。房间活动投影在聊天回应上提供 `chatOnly`，界面与服务端均不向主持聊天运行追加行动插话。下一次行动恢复正常裁定工具与接续逻辑，房间协议版本保持 `1`。

## 待提交行动替换与撤回

`ChatTurnQueue.replacePending` 与 `convertToChat` 是真人和队友共用的修改入口。新行动保存时在同一写事务内将本人旧行动改为聊天，不影响其他作者；发送失败整体回滚。切到自动模式后发送新行动，也先替换本人的旧行动，再把其他参与者的待提交行动一起交主持。已保存发送请求的重试只返回旧消息的最新版本，不会恢复其行动身份。

`chat.convertToChat` 按认证玩家身份校验所有权，只允许将本人的完整待提交行动改为聊天；按指定消息 ID 幂等，重复请求不影响后来的新行动。主持输入批次从创建起冻结原文，`ChatInputBatches.isPreparedSource` 保护仍在准备或等待恢复的来源；已开始提交且不再待提交的消息同样拒绝转换。更改消息通过正常版本通知同步到所有客户端，旗帜、待提交状态和对应操作入口随转换消失，不删除历史或新增「已替换」状态。

队友每轮额外取得自己的 `pendingAction: { id, text }`，即使该消息已超出近期事件窗口仍可明确定位。`companion_withdraw_action` 通过消息 ID 调用上述转换，仅能操作当前队友本人的消息。成功结果落盘后正常结束本轮；普通聊天和沉默不撤回旧行动，失败工具允许继续纠正。只撤回而没有新发言的回合隐藏空正文，真实工具记录仍保留在 Pi 会话和推理详情；直接点名下成功撤回也算有效回应。旧消息的 `chatOnly` 与 `pendingAgent` 更新会作为事件变化在队友后续调用时补入上下文，提示词要求不再把该讨论当作待执行意图。

## 普通主持输入交接

真人和队友的行动经 `PlayerTurn` 进入同一套批次提交与恢复流程。输入接收表示已进入模型会话，与工具执行成功或裁定完成分别记录。

普通主持输入批次在内部 `chat_input_batches` 表持久保存，公开主持消息的 `inputBatch` 只含标识与接收状态；内部记录包含稳定批次 ID、有序来源 ID、提交时原始行动和身份快照，以及 prepared/received/abandoned 状态。内部表在新冒险建立，首次使用时也可初始化空表。创建批次与主持占位消息、领取来源消息在同一事务内完成；来源从 pending 列表移除只表示领取。`Runtime.run` 接收该批次，在承载实际输入的原生 custom_message 中同时写入内部 batchId/messageId 标记，使用 `onInputReceived` 通知应用事务确认并消费来源。标记位于 details，不进入模型正文。宿主无 Pi 历史时须主动报告接收；成功返回可作为最后确认，失败不能推断已接收。

原生写入成功但应用确认失败时，恢复流程沿有效 Pi 分支查找接收标记并补齐事务；未接收批次原样保留。房间活动投影通过 `pendingInput` 指明未送达批次，不依赖聊天分页。房主调用 `chat.resolveInput` 重试或放弃；重试使用原始批次与身份，新状态仍按当前存档核对；放弃保留原聊天、不调用模型。重试已接收批次时返回原消息，不再次生成；已接收批次不能放弃。存在未送达批次时拒绝新行动，允许仅聊天及相关点名；队友新声明不自动交主持。重启和取消不自动调用模型。接收只表示输入进入会话，完成、失败、部分保存及取消仍按既有运行语义处理。

## 主持插话

领域用语见[房间协作术语](GLOSSARY.md)，应用持有可撤销队列的取舍见 [ADR-0001](adr/0001-应用管理主持插话队列.md)。

### 行为与聊天顺序

主持插话默认关闭，房主在冒险设置开启，按房间持久保存。仅支持正在运行的 AI 主持，AI 队友保持原有生成与中断行为。所有有权提交行动的玩家均可插话，沿用身份、角色和房间访问检查。

| 项目       | 行为                                                                                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 输入       | 开启后，主持生成期间的普通行动发送按钮显示为“插话”；自动和手动提交模式均可排队。“仅聊天”保持原行为。                                                   |
| 队列       | 独立展示，所有玩家可见；未接收内容不进入聊天历史，也不额外唤起被点名的 AI 队友。                                                                       |
| 容量       | 每人最多 2 条、全房最多 5 条，包含待接收和待提交插话；去除首尾空白后非空，最多 4000 个 JavaScript 字符单元。超限明确拒绝、保留草稿，不自动删除旧条目。 |
| 删除       | 玩家只能删除自己的条目，房主可删除任意条目；删除仅移除卡片，不生成撤销消息。已接收内容不能通过队列撤回。                                               |
| 普通接收   | 当前响应与本轮全部工具结束后，按主机收到的顺序一起接收仍符合条件的插话，继续同一次主持运行。等待玩家掷骰也属于工具执行，不被普通插话打断。             |
| 直接打断   | 仅房主可操作；先停止并等待旧运行退出，再将整个队列按顺序交给新运行。房主可先删除不需要的条目。                                                         |
| 停止与恢复 | 生成结束、停止、失败、关闭房间或重启后，未接收内容保留为待提交，等待房主显式提交，不自动续跑。                                                         |
| 关闭开关   | 停止新插话与自动接收，旧条目转为待提交；仍可按权限提交或删除，重新开启不自动消费。                                                                     |

主持未运行时，普通行动遵循自动或手动提交方式；已有插话队列仍等待房主提交。结束边界新到达但未进入当前运行的插话保留为待提交，不改为普通自动行动。接收、撤销、关闭与打断以服务端顺序裁定归属。

普通接收的时间线是：保存主持消息 A 的已有内容，将本批插话持久纳入上下文，按入队顺序投影为保留作者身份和原文的玩家消息，再创建主持消息 B。A、B 属于同一运行，不用旧消息中的分隔文字代替新消息。直接打断时保留 A，由新运行生成 B。

同一房间只有一条活动 AI 运行。打断保留已有文字、已保存文档和已完成骰子结果，未完成骰子标记失败；已经开始发布的文档批次可能继续完成。新运行依据当前存档和实际工具结果，不重复结算。

### 队列、权限与同步

`game.steering.enqueue` 入队，其他接口提供完整快照、按条删除、开关及整队列提交。SQLite 独立保存插话，与普通待提交行动分开，不从最近一页聊天筛选队列。房间协议版本保持 `1`；`steering_requests` 保存条目及请求终态，`steering_batches` 保存交接批次与显式提交去重，`steering_meta` 保存快照版本。

条目保存稳定 ID、请求 ID、作者玩家 ID、原文、入队顺序、创建时间及自动接收或手动提交归属；聊天消息 ID 在接收投影时关联。作者来自认证上下文，不信任客户端自报身份。容量与长度在服务端检查，容量检查和入队在同一事务内完成。请求按玩家 ID 与请求 ID 持久去重，已撤销或已接收请求重试不重新排队；批次也使用稳定标识，避免重复投影或注入。

开关为 `settings.json.chat.steeringEnabled`，默认 `false`。关闭时先保存队列的待提交归属，再保存设置；两者没有联合事务，保存失败不自动消费旧条目。

`GameContext.isHost` 由宿主适配层提供，缺省为普通玩家，桌面本地原生桥 明确赋予房主能力。开关、删除他人条目、显式提交、直接打断，以及停止、切换提交方式和手动继续均在游戏路由验证房主权限；不能信任客户端传入的 `isHost`，也不能仅隐藏按钮或允许绕过路由调用停止能力。作者权限按稳定玩家 ID 判断，不按昵称。

队列变化通过房间订阅同步，重连恢复完整快照；通知与 RPC 响应按持久 `revision` 合并，避免旧入队响应复活已删除条目。提交或删除遇到已接收条目时明确报告冲突并刷新状态。当前运行通过 `sections.chatActivity` 同步，接收后保留 `runId`、更新 `messageId`；停止接受当前消息或原始运行标识，不从已加载历史判断活动状态。工具结果、骰子位置、公开增量、推理详情及 Pi 历史范围随消息切换，公开增量与详情流重新编号。

### Pi 交接与恢复

应用保留未接收队列，在 Pi 公开 `turn_end` 安全边界返回 `custom_message` 并请求继续，保留 Pi 原生压缩、工具调度、取消与上下文投影。交接串行核对开关和运行状态、选定条目、锁定 SQLite 批次、写入 Pi 上下文，再提交聊天投影与队列变化。包装原生 `appendCustomMessageEntry`，成功写入后由 SQLite 同一事务确认队列终态、投影玩家消息并创建新主持消息。手动提交先保存内部占位，Pi 保存批次标记后才将其移动到玩家消息之后并公开。

“已接收”指插话已持久进入主持上下文，且可据此恢复聊天投影，不表示模型已成功回答。Pi 原生条目保存稳定插话 ID、批次 ID 与运行关联；开始生成、取出内存队列或发起 HTTP 请求均不是接收凭据。锁定后的删除或关闭操作不能将已进入上下文的内容误判为未接收；临时锁在失败后释放或通过对账解决。

SQLite 与 Pi JSONL 没有联合事务，恢复按实际有效会话分支的批次标记及稳定条目 ID 对账，不按文本或游戏记忆摘要推断：

| 故障位置                          | 恢复要求                                               |
| --------------------------------- | ------------------------------------------------------ |
| Pi 上下文写入前失败               | 不确认接收；释放未落盘批次的锁，保留为待提交。         |
| Pi 已写入，聊天投影或队列更新失败 | 补齐玩家消息、主持消息关联和队列终态，不再次注入。     |
| 接收后模型生成失败                | 保留已接收聊天与上下文，沿用生成失败处理，不重新入队。 |
| 停止、关闭房间或进程重启          | 对账后将仍未接收的条目保留为待提交，不自动续跑。       |

对账先于队列操作与新主持运行，避免已进入 Pi 的条目仍可删除。直接打断使用同一批次交接流程：停止失败、房间关闭或新运行无法启动时，未接收内容仍留队列，不能点击即清空。交接期间新条目按入队与锁定顺序归属，不扩大已锁定批次。

核心回归覆盖多人容量与权限、撤销去重、整组工具后的真实 Pi 接收、聊天分段、SQLite 投影失败重启恢复及直接打断。测试入口与维护原则见[测试维护](测试维护.md)。

## 会话生命周期与上下文查看

Pi runtime 按会话文件复用 `SessionManager`，主持与各队友使用独立实例；每回合仍重新创建 AgentSession、工具、模型配置和提示词，结束后释放该回合监听器。复用前比较文件身份、大小与修改时间；文件变化、运行失败或取消时，下次从磁盘重新加载。运行、详情和统计共用这份缓存，并发加载同一文件只创建一个管理器；活动实例不淘汰；运行结束后的实例按最近使用顺序释放，缓存预算为八个管理器、所对应的文件大小合计 64 MiB；这是缓存预算，并非 JavaScript 堆内存上限。房间关闭时释放该房间全部管理器，重开房间从存档恢复。

会话统计中的上下文查看通过本机 `sessions.ai.context` 读取 `PiHistory` 的原生有效会话投影，复用运行中的管理器；按消息注入顺序分组，系统提示内部保留 Pi 命名板块的插入顺序。包含压缩记忆、有效消息、工具定义与调用结果，不拼接已被摘要替代的旧历史。已有可读思考独立于聊天显示设置，加密内容仅标识存在。此接口不调用模型、不初始化空会话；未进入 Pi 会话的排队消息和流式片段尚未计入。快照只在弹框打开或手动刷新时读取，不进入实时房间投影；复制包含全部可读文本，图片仅复制类型标记。实际请求转换、思考回传、压缩和用量统计保持 Pi 既有行为。

上下文调整只作用于新输入和新工具结果，不重写原生会话历史，也不逐轮删除旧快照；历史冗余由游戏记忆压缩处理。上下文查看使用原生有效投影，与实际采用的系统板块和消息一致。模组简介与手册调整通过新冒险或显式同步生效，不自动改写冻结模组。

## 游戏记忆压缩

主持与 AI 队友均通过 `game-compaction.ts` 的内置扩展接管 Pi 的 `session_before_compact`。阈值、切分边界、最近消息保留及摘要落盘继续由 Pi 管理；扩展只使用本会话待压缩的消息、长回合被切开的前半段和上一份摘要，不读取其他会话或额外游戏资料。

摘要使用中文 Markdown，优先保留人物关系、已知线索及知情范围、未完成事项、主持承诺与裁定、当前进展和中断位置。主持的幕后信息单独标记为未公开；队友仅整理自己收到的信息。工具结果附带工具名与失败标记，提示摘要模型区分声明、内部计划、实际提交、取消和部分成功，避免把待裁定行动写成完成或重复结算。

摘要不是状态来源。主持继续裁定时仍须读取当前游戏存档，队友以本轮公开事件、订阅字段或按需读取的公开资料为准；生命、资源、物品、位置等可变数值不作为摘要中的当前数值表保存。摘要更新时合并旧记忆与新记录，已失效计划可以被移除；原始 JSONL 历史不删除，推理与工具详情沿原生条目链读取。

摘要请求通过当前模型的 `ModelRegistry.streamSimple` 使用宿主配置的认证与服务商，复用压缩取消信号，关闭一次性摘要请求的提示缓存写入。输出上限取 4096 Token、预留空间的 80%、压缩阈值的一半和模型输出上限中的较小值；用量写入 Pi 原生压缩条目。文本序列化复用 Pi，实现中的工具结果裁剪仍适用。摘要语义由模型生成，不提供无损记忆保证。

生成报错、被截断、返回空文本或工具调用时，扩展明确取消压缩，保留原上下文，不回退到 Pi 的通用代码摘要；本轮生成停止并向调用方返回压缩失败原因。用户取消时按统一取消机制处理，不保存摘要。压缩成功才返回原始 `firstKeptEntryId` 与 `tokensBefore`，由 Pi 追加检查点并刷新后续上下文。

手动压缩由桌面本机接口 `sessions.ai.compact` 发起，指定主持或某个队友，复用对应角色的模型、阈值与游戏记忆扩展。`ChatService` 占用房间操作互斥，runtime 以 `operation: "compact"` 调用 Pi 的 `compact()`，不追加玩家输入或聊天消息。压缩中的角色 ID 随房间统计推送；成功、失败均释放互斥并通知刷新，关闭房间先取消压缩再等待资源释放。

## 房间笔记

每名玩家在每个房间拥有一份纯文本笔记。内容以稳定玩家 ID 为键保存到 `adventure.json.notes`；改昵称不改变归属，玩家不能读写彼此的笔记。笔记与聊天切换时保持挂载，不中断聊天生成；不提供多份笔记或 Markdown 预览。

停止输入 650 毫秒后自动保存，卸载、切换房间或玩家时尽力立即保存。同一份笔记的读写按序执行。输入同时保存本机草稿，落盘成功后清理；失败可重试，下次进入恢复。本机存储不可用时只保留进程内草稿，清除应用本地存储会删除尚未落盘的草稿。

接口为 `sessions.notes.get({ roomId, playerId })` 和 `sessions.notes.save({ roomId, playerId, content })`。主进程按请求身份读写，`playerId` 只核对界面所属玩家；身份切换后的旧请求被拒绝。每份笔记上限 200,000 字符，未填写时返回空文本，不依赖 SQLite。

组件为 `features/sessions/RoomNotes.tsx`，以房间和玩家组合为 React `key`；本机草稿键为 `tarp:room-notes-draft:v2:<房间 ID>:<玩家 ID>`。

## AI 队友调度与公开投影

真人和 AI 共用角色占用检查，主持与队友串行运行，每房间最多一条 AI 运行。玩家发送非聊天、非点名行动后，积极与活跃队友先按席位判断是否补充自己的行动；已有待提交行动的队友跳过，不覆盖其意图。是否同场景不影响参与讨论的机会。手动模式将玩家和队友的各自最新行动留在待提交列表，自动模式收齐补充后统一交主持；队友沉默、生成失败或凭据不可用不会阻断其余补充与自动提交。主动停止不自动交主持，待提交行动保留。积极队友不在这批裁定后重复唤起；其他档位在裁定后判断，活跃队友还可在自己的行动裁定后再次判断并继续推进，直到沉默或玩家停止、介入。普通聊天不触发该阶段，明确点名仍走独立回应队列和连续点名上限。队友会话与主持会话隔离，互动主动性与独立模型保存在席位，从下一次调用生效。

队友未点名时通过 `companion_perform` 的 `text` 发送纯聊天、通过 `companion_request_ruling` 的 `intent` 提交行动，同一轮可先聊天再提交一次行动，完成时分别保存为聊天消息和行动消息。行动正文可以同时包含动作和台词。两种工具均从正文解析身份链接；若某次工具调用包含合法点名目标，该调用归为聊天，即使使用行动工具也不进入主持待提交队列、不替换已有行动；不会影响同轮另行提交的不带点名的行动。两种工具正文仍流式展示，可选 `<action>` 标签只控制展示样式。

`chat.mentionTargets` 是候选与模型上下文共用的公开身份入口。主持使用固定身份 `agent` 且 `kind=host`，真人使用玩家 ID，AI 使用已入队席位 ID；角色文档 ID 只用于控制关系。真人昵称优先取当前连接，其次最近玩家发言与准备卡片；角色名使用公开文档投影。队友上下文明确提供参与者身份、所控制角色及公开 NPC 发言；主持只接收统一的玩家与角色名单，通过稳定身份关联发言与角色。历史点名名称不随改名更新；失效目标从 `mentions` 排除，正文保留并按原手动模式发送。普通文字中的 `@名字`、`@ID` 不建立点名；完整且有效的身份链接才建立点名。

`ChatMentionQueue` 和主持行动队列独立，每房间仍只运行一个模型。点名的触发消息与全部 `queued` 回复在同一个 SQLite 事务中保存，`replyToMessageId` 指向触发消息；任何目标保存失败整批回滚。事务提交后、公开通知发布前同步登记内存任务，再启动调度，避免通知消费者把有效排队任务恢复为中断。AI 完成消息及其自动点名回应也共用这一边界。生成结束后真人点名优先、同类先进先出，同一消息目标去重、自点名不再唤起。每条链读取房间 `chat.mentionReplyLimit` 快照，默认八条、范围 1–32；计数随主持裁定保留，网络重试与空回复补问不重复计条。达到上限取消剩余响应并显示原因。凭据或上下文准备失败时，已保存的回应标为失败。停止或关闭清空排队响应、取消当前运行，异常重开将遗留等待消息标为中断，不自动重放。

主持成功完成后，从本次运行各条公开消息的旁白及 NPC 分段解析身份链接；失败尝试、停止和中断的草稿不调度。插话切换后仍按原消息关联触发来源，全部回应与确认记录共用写事务；重开不重放。主持点名与 AI 接话同属自动优先级，低于真人点名，先于本轮普通自动反应；已点名队友从本轮普通反应列表排除，其余队友照常判断。点名不受主动性档位或角色位置限制，接收者取得房间公开时间线，角色位置与知情范围仍按模组规则解释；点名链经过队友行动和主持裁定时复用计数，不能通过主持再次点名重置上限。

玩家普通行动打断正在思考的队友时，先取得运行交接保护，再停止并等待队友，持有保护直到玩家消息保存和必要的主持启动完成。其余点名任务保留在队列中，不能在旧队友结束时抢先占用运行槽；手动提交完成后或主持结束后继续正常调度。提交失败也释放交接保护，不留下永久等待的队列。

调度只读取提交入口或运行收束确认的 `message.mentions`。AI 接话使用已持久化的完成消息作为触发来源，避免把重试失败草稿带入下一次点名。主持、队友、朗读与模型上下文共用成功消息筛选；运行中、失败和停止仍保留已经流出的草稿。编辑器的原子标签只作为本地草稿结构，发送时生成含身份链接的 Markdown 正文；手写完整身份链接与候选选择遵循同一规则，输入用途、重试、提交与队友工具均按正文解析。复制同时写入明文名称与 `application/x-tarp-mention-draft` 编辑器标签；应用内回贴验证身份；外部明文粘贴不按名称猜身份，完整身份链接仍参与统一解析。

被点名队友的上下文附带触发消息 ID、作者身份（包括主持来源）、字符串正文与点名目标。房间公开聊天和叙事均可进入上下文；角色位置与知情范围由模组规则和主持裁定解释，玩家获知公开交流不等于角色亲历或自动获得远处信息。

模型可自由判断聊天或提交不带点名的行动；主动判断通过无参数的 `companion_silent` 明确选择沉默，不要求或记录原因，也不展示聊天正文；沉默与聊天、行动互斥，直接点名禁止沉默。沉默或真正提交行动成功后，在工具结果落盘后的回合边界正常结束，不再请求模型收尾；失败工具、纯聊天及含合法点名的行动工具调用仍允许继续。若既未有效发言或行动，也未明确选择沉默，Pi runtime 在原会话补问一次，不重跑工具；补问期间在幕后详情提示，主动判断补问后仍无发言则按沉默隐藏；直接点名补问后仍无有效回应才显示失败。队友没有世界写入、裁定或掷骰工具，向 NPC 发言交给主持；普通聊天不作为主持背景；点名主持时仅本次消息进入主持场外聊天。合法点名消息不参与主持插话。

移除队友释放角色控制权；重新分配会创建新的队友身份，不自动恢复已移除身份的记忆。生成期间需先停止，再修改单名队友的分配。

真人与 AI 共用角色预留：选中即预留，取消或换选释放旧角色，确认后才绑定。同一张角色卡不能同时被真人与 AI、或多名 AI 占用。队友提示词只从冻结模组的预设读取，不会为缺少预设的角色自动生成提示词。

房间投影的 `companionVersion` 覆盖当前开局、角色归属与退役、真人选角预留、队友席位和文档版本。渲染端的 `useRoomCompanions` 在版本变化后取消旧查询并刷新共享队伍缓存；聊天、开局组队和冒险小队使用同一入口，避免选定开局前发起的空查询在延迟返回后被当作有效候选列表。队友流程命令同时合并响应中的开局版本，下一次操作无需等待订阅通知即可取得最新版本。

队友每轮接收自己的角色身份与当前公开参与者；首次提供加入之后的近期公开事件，后续仅提供新增或内容变化的事件。事件 ID 不变时视为原事件更新，例如待提交行动已交主持；未变化的事件不重复写入持久会话。运行时在正常完成后追加 `companion_event_receipt` 元数据，记录事件 ID 与内容摘要，不进入模型上下文；失败和取消不确认接收。接收记录沿原生会话分支恢复，重开与记忆压缩后继续生效。没有接收记录的会话首次仍提供近期背景。队友依靠自己的会话历史、游戏记忆摘要和按需查阅延续经历，不通过每轮重放近期聊天维持记忆。主持原始状态、GM 字段、文件目录、工具、内部推理和加入之前的聊天不传入队友。位置、场景、同行和参与情况按模组规则与主持已裁定事实解释；平台不自动安排队友入场、不按场景限制公开接话，也不向消息或队友上下文注入场景标记。

队友的 `documentAccess` 默认关闭；开启后提供专用 `find` 与 `read`，查阅范围与普通玩家一致，不随房主的调试展示扩大。角色正文、数值和完整状态不逐轮注入，详细资料按需查询，或由已开启的上下文订阅提供。`find` 按公开名称、简介和类型筛选并分页，返回资料 ID、公开名称、类型和可选简介；`read` 通过 ID 读取当前公开计算投影，复用 `isDocumentVisible` 和 `publicGameDocuments`，不返回主持字段、隐藏原值、公式、目录或配置。结构化引用和 Markdown 文档链接转换为公开资料 ID，隐藏引用不返回；已撤销揭露的 ID 与不存在的 ID 使用同一拒绝结果。查询在文档锁内复用共享计算快照，每次检查当前可见性。队友仍没有文件写入工具。

主动判断会增加模型调用，即使最终选择沉默也可能产生用量。沉默结果不展示聊天正文或“没有回应”占位；主动判断补问后仍无发言按沉默处理，被点名后仍无有效回应才显示失败；下一条消息会开启新回合。停止、中断和失败不会自动发起主持裁定，重开房间也不会自动续跑未完成请求。

队友席位与选角预留保存在房间的 `adventure.json.party.companions`，已入队席位直接保存该队友的模型、主动性、文档查阅开关和声音偏好，随队友一同更新和删除。队友席位的 `id` 是该 AI 队友固定的虚拟 `playerId`，同时用于角色控制权、聊天发送者、主持输入、检定身份和独立会话；重启后保持不变。移除队友会删除该虚拟玩家，重新添加时创建新的 `playerId`。

每次调用从冻结模组的预设和当前队友配置构建输入；角色设定之前注入本局 `companionRoleplayPrompt`，未自定义时由 `companionRoleplayInstructions` 提供内置扮演指导。它约束情境化扮演、关系连续性和自然表达，减少空泛安慰、排比承诺、装饰动作与固定问句收尾；所有队友共用，身份、信息边界和工具协议另行固定追加。应用默认值在创建时解析为正文并随房间保存，之后默认值变化不影响已有房间；房间编辑或恢复内置指导从下一次调用生效。主动性设置只决定参与时机，不替换扮演指导。

按 `documentAccess` 注册只读资料工具并注入对应使用指引；更改权限从下次调用生效。新增队友时复制冒险 `companion.documentAccess` 默认模板，后续模板修改不改变已有队友。查阅工具与结果不进入公开聊天，由 Pi 会话保存，通过推理与执行细节入口读取。公开 AI 消息使用 `companionId` 区分说话人。独立会话保存在 `agent/companion-<队友ID>.jsonl`，主持使用自己的原生会话。双方共用用量统计和取消机制。

Pi 的 session JSONL 保存并恢复完整模型历史。队友每个新回合的提示通过 `companionContext` 读取 SQLite 中入队后的近期公开发言，包含未点名的纯聊天，并按接收记录只注入新增或变化的事件。事件保留 `chatOnly` 与 `pendingAgent`，提示词明确区分讨论、行动意图和待主持处理的状态；纯聊天只用于理解讨论，不视为已提交行动或裁定结果。

## 掷骰

玩家不能主动发起自由掷骰。主持人查阅规则并确定目标、难度与修正后，通过 `roll_dice` 发起公开检定；支持 `1d20`、`2d6+3` 等表达式，可填写检定用途。当前支持 1–20 颗骰子、2–1000 面，以及 ±1000 内的固定修正值，不支持优势、爆骰或混合骰面表达式。

主持人指定真人玩家掷骰时，会在聊天中创建互动卡片，仅该玩家可点击；30 秒内未点击由主进程自动结算。未指定玩家或指定 AI 队友时立即结算，AI 队友没有点击入口。主持人等待真实结果后继续叙述。正常返回的结果进入 Pi 工具历史；后续请求不附带最近掷骰清单，不补送中断工具的结果。

结果使用主进程的安全随机数生成器，在数据库事务中保存，再发布给所有订阅者。重复请求、重复点击和超时竞争不会产生第二份结果。主持运行终止后，所属未完成骰子标记 failed 并取消倒计时；重开房间时遗留未完成骰子也标记失败，不恢复结算。失败卡片保留但禁止点击或超时结算。已完成结果不变；点击结算与终止竞争时，以数据库先保存的终态为准。

前端展示倒计时、骰子翻转和结果落定动画，尊重系统减少动态效果设置。动画不参与结果计算，历史结果直接展示。公开骰子是一种房间业务消息，不塞进 pi 的 assistant 文本模型；AI 发起的卡片按工具调用位置插入检定前后的叙述之间。

## 主持资料检索

主持系统提示词每轮生成一份按类型分类的资料索引，保留类型名称、说明、字段定义路径，以及各文档目录的数量，不另列重复目录树。类型名与 ID 相同时只显示一次。一级目录决定类型，同一类型可以继续嵌套资料分组；本局新增文档也会进入索引。文件夹与文件分别显式标注，文件夹路径相对工作区，文件名相对所属文件夹。每个类型在同一目录内不超过 20 个文档时列出真实文件名，由模型按 `文件夹/文件名` 拼接读取路径，不添加类型后缀。超过时提示用 `read/find/grep` 按需查询。索引不展开文档或字段定义正文；文档按类型与目录一次分组，字段定义只枚举一次并提供完整路径。

`read` 遇到不存在的路径时，如可读资料中存在同名文档，会在错误中列出至多 10 条实际路径供模型纠正；不自动选择文档或读取正文，越界、符号链接和多格式冲突仍按原校验拒绝。

主持查阅规则时应先按类型定位目录，再使用目录或搜索结果中的真实路径读取，不能根据主题猜文件名。`find` 的结果相对于搜索目录，交给 `read` 前需要补齐目录；`grep` 返回的文件路径相对于游戏工作区。该分类目录只提供给主持，不传入 AI 队友上下文。

游戏文档的 `read`、`update`、`batch_update`及 `grep` 文件目标统一忽略最后的 `.json/.toml/.md`，例如 `规则/战斗/先攻` 与 `规则/战斗/先攻.md` 定位同一份文档；必须保留类型目录及完整分组路径。同名多格式直接报错，完整路径也不能绕过冲突。响应使用 JSON，`path` 返回规范实际路径，版本和缓存不会按输入别名分裂。`write` 接受同样的路径写法，新文档统一保存 JSON；批量更新按文档身份拒绝重复目标。目录与字段定义使用实际路径，`find` 的 glob 保持真实文件名匹配。

`update` 和 `batch_update` 全部保存成功后仅返回 JSON 字符串 `"Success"`。工具层不回传文档内容、路径或版本，避免重复内容累积进入模型上下文；内部保存接口仍保留完整结果。需要核对更新后的计算值时通过 `read` 获取。失败时仍保留已保存与未保存路径等恢复信息。

主持 `read` 支持可选 `fields`，按相对文档 `content` 的 JSON Pointer 选择字段，支持嵌套对象、数组索引及 `~0/~1` 转义。局部读取的 `content` 是指针到值的映射，相关 `_字段名` 原值一并保留；路径、版本、计算错误和角色运行信息仍返回。缺失字段或无效指针报错，目录不接受 `fields`；省略时保持全文读取。选择发生在权限校验和完整计算之后，只减少模型输出量，不改变计算依赖。字段定义的 JSON/TOML 源文件统一解析为结构化 `content`；`fields` 使用定义对象中的 JSON Pointer，局部返回指针到定义值的映射，并以 `constraints` 附带必要祖先字段约束，省略祖先的 `fields/item` 子树。完整读取保留全部定义，字段定义始终只读。主持每轮仅附带世界文档路径及角色身份与路径索引；世界和角色的完整状态不自动注入。裁定所需状态使用本轮订阅字段或按需读取，本轮读取后未变化的字段无需重复读取。

`grep` 搜索合并后的原始字段与解码后的 Markdown `body` 行，避免正文的 JSON 转义影响按行搜索、上下文和截断；计算后的公开值仍通过 `read` 获取。

主持文件工具共用允许访问的文件集合：已注册类型的游戏文档，以及 `.types/*.fields.json/toml` 中对应已注册类型的字段定义。目录读取、`find`、`grep` 和初始目录索引只披露这些文件及其父目录；`read` 拒绝直接读取模组配置、布局、附件或未注册类型文件。每次查询重新枚举，本局新增文档立即可查。文档按基础模组与本局覆盖规则合并，字段定义只读；此限制不影响应用自身加载配置与展示图片。

### 工具结果与读取范围

结构化模型工具结果使用紧凑 JSON，不改变正文字符串或 grep 的定位行。主持默认读取省略实例 `$instance` 展示元数据（完整文档及选择容器字段均适用），计算状态和原值别名保留；JSON Pointer 显式选取 `$instance` 时仍可读取。界面投影不变。队友通过引用物品的实例字段定义转换公开动态状态，递归处理公开引用和 Markdown，不能因空的静态状态字段定义将值清空，也不能复制主持原值或隐藏字段。明确的状态核对优先 `fields`，允许完整查阅未知资料；不自动生成摘要视图或添加默认订阅。codemode 批量查询先用 `fields` 缩小读取范围，再在脚本内解析、筛选或计算，仅输出本次裁定所需的依据、结果和相关路径；计算需要的原值与更新约束不得省略。未知规则可全文查阅，不对规则或工具结果做自动截断。

## 上下文订阅

`contextSubscriptionsEnabled` 随应用默认配置与房间配置保存，默认关闭。开启时，运行时向主持裁定和有查阅权限的 AI 队友注册 `context_subscribe`；主持场外聊天不注册该工具。工具支持按文档替换字段清单、取消、列举和清空；设置订阅时立即返回当前字段值。清单保存在 `adventure.json.contextSubscriptions`，以主持或队友身份隔离，只保存文档定位与 JSON Pointer，不保存状态值。关闭开关保留清单，停止工具访问和后续注入；重新开启后恢复读取。

正常输入、主持插话及队友点名补问在追加消息前重新读取订阅字段。主持复用游戏文档读取与计算投影，包含选中计算字段所需的原值；队友复用普通玩家可见的文档投影，不能取得隐藏字段、原值、目录或配置，并在读取前后检查活跃身份与 `documentAccess`。文档、字段失效或可见性撤销时只提供不可用提示，不沿用旧值；查阅权限撤销后停止注入。每个身份最多 16 份文档、100 个字段，每次注入的字段快照预算为 32 KiB，超限文档提示缩小范围。

订阅只追加到本轮新消息，不改写已有消息；同一轮工具执行后的修改仍需按需重读。稳定的历史前缀得以保留，但开关改变工具定义、其他系统上下文变化与服务商策略仍可能影响缓存。自动附带字段会增加输入 Token，但可能减少额外的读取请求；设置界面明确说明这一取舍。

## 数据与恢复

房间文件职责、`module/` 与 `game/` 的合并规则及格式边界见[游戏房间存档格式](游戏房间存档格式.md)。房间存档按当前格式校验。

删除或修改原模组不影响已创建的房间。房间副本不跟随符号链接，工具拒绝访问副本之外的路径。不会自动执行模组携带的扩展或加载用户的全局 Pi 扩展。

同一房间的并发 `closeRoom()` 共享关闭任务，所有调用者都等到资源释放结束；关闭期间拒绝新的房间访问。某项清理失败后仍继续执行其余清理，最后汇总错误并移除旧连接，允许后续重新打开。服务级 `close()` 等待全部房间关闭后再报告错误，不因某个房间先失败就提前结束。

回复增量合并后先写数据库，再发布，短暂断线按事件流标识与游标补发内存通知，通知过期时重新读取消息快照。失败或取消保留已收到的部分回复。应用异常关闭后，未完成回复标记为中断，不自动再次请求模型。

发送与继续请求通过 SQLite 的 `chat_requests` 持久去重，以 `(player_id, operation, request_id)` 为唯一身份；`send` 和 `continue` 分开，发送内容的摘要不同则报冲突。请求记录、玩家或主持消息、待提交集合消费在同一个事务中提交，失败全部回滚。内存只合并正在执行的 Promise；异步准备后及写事务内再次核验记录，已提交请求始终读取消息最新版本。记录随冒险保存，不因关闭房间、主进程重启或其他请求增多而淘汰。重试已提交但失败、取消或中断的请求时，只返回已有结果，不重跑模型；需要继续冒险时发起新请求。

主持与 AI 队友启用 Pi 原生模型请求重试：网络中断、短时限流和服务端临时错误最多重试三次，依次等待 2、4、8 秒。重试继续使用已完成的工具结果，不重新提交玩家输入、不重跑整轮游戏操作；同一条聊天消息保持运行状态，最终请求成功后才标为完成。认证、账户额度等不可重试错误直接失败；停止生成也会取消重试等待。原生会话保留失败尝试，模型上下文由 Pi 排除待重试的失败响应。

不提供应用层整轮 AI 回合重试。重试耗尽后的失败和取消保留已公开的消息与已提交的游戏状态；下一条玩家消息开启新回合。开场失败时可从当前游戏状态继续开场，创建新的 Pi 回合。游戏记忆压缩与插话交接错误独立保留，不因后续模型请求成功而被清除。

## 接口与通知流

游戏契约定义于 `packages/core/src/shared/game.ts`。业务接口包括 `chat.send`、`chat.continue`、`chat.setSubmissionMode`、`chat.mentionTargets`、`chat.setMentionReplyLimit`、`chat.get`、`chat.history`、`agent.cancel`。实时更新通过 `room.subscribe/acknowledge` 的统一房间通知流接收，提交方式的初值随 `chat.history` 返回。

房间投影的 `sections.chatActivity` 独立保存当前运行的 `runId`、当前 `messageId`、说话人信息及最早排队回应，不依赖聊天历史分页。启动、结束、取消和插话导致的消息切换都通知投影刷新；运行中的 `messageId` 可变化，`runId` 保持稳定。输入区据此判断生成、停止与插话，收到首次活动快照前不开放提交。取消接口 `agent.cancel` 使用 `messageId` 字段，停止当前运行时传 `runId`，仅有排队回应时传排队消息 ID。

### 消息结构

- 房间消息保留自身的 ID、房间 ID、顺序、发送者、昵称、状态和时间。玩家消息使用 `text`。
- 手动提交的消息用 `pendingAgent` 标记；队友提交的行动正文保留在 `pendingAction`。真人与队友均只保留本人的最新一条待提交行动，旧行动转为 `chatOnly=true` 并清除 `pendingAgent` 与队友的 `pendingAction`，保留原正文。纯聊天不带待提交标记，也不替换已有行动。玩家消息的 `chatOnly` 表示不作为行动提交给主持裁定；未点名闲聊按可见范围进入队友后续上下文，合法点名聊天还可以唤起主持或队友。发送与继续的幂等记录保存在 `chat_requests`；提交方式及其版本保存在设置文件的 `chat.submissionMode` 和 `chat.submissionModeRevision`。
- AI 回复的 `agentMessages` 使用 pi 的 `AssistantMessage[]`，保留模型、供应商、用量、结束原因和时间；一次回复内的多次模型调用分别保存。
- 主持公开内容只保留文本块；队友仅公开纯聊天和提交行动对应的工具调用。思考、其他工具调用、工具结果、签名和原始错误不进入公共聊天。完整 agent 上下文由房间的 Pi 会话保存。

### 增量与恢复

聊天订阅事件包括：`message` 提供创建和终态快照；`agent` 携带精简的 `message_start`、`text_start`、`text_delta`、`text_end`、`message_end`；`mode` 同步房间提交方式快照；`steering` 同步插话队列快照。文本增量只传新增字符，不附带 pi 的完整 `partial`；文本结束及消息结束时携带最终内容用于校准。这是 pi 事件的公开投影，并非原始事件直接透传。

提交方式统一使用 `SubmissionModeSnapshot = { mode, revision }`：`chat.setSubmissionMode` 返回快照，`chat.history.submissionMode` 携带快照，`mode` 事件使用 `snapshot` 字段。房间创建时版本为 0，模式变化时递增，与模式原子保存到设置文件；相同模式不增加版本，其他配置更新保留版本。保存成功后直接发布通知，不开启空 SQLite 事务；保存失败不发布事件。客户端从通知、RPC 响应和历史读取快照，只接纳比已知版本更新的值，重复或迟到快照不覆盖当前模式。恢复时以设置文件为准。

主进程约每 100ms 合并同一文本块的相邻增量，在 SQLite 事务中更新完整消息并暂存通知；事务成功后发布到内存缓存，回滚时丢弃暂存通知。每个数据库连接拥有独立的事件流 UUID，缓存最多保留 1024 条事件、总计 8 MiB；超出窗口的通知不再补发。历史读取完整消息，不从事件重建。

`chat.history` 同时返回 `streamId` 和 `cursor`，订阅通过 `afterChatStreamId` 与 `afterChatCursor` 指定补发位置。流身份变化、游标超前或落出缓存窗口时，返回 `CHAT_RESYNC_REQUIRED`。客户端从最新消息开始向前分页，覆盖此前已加载的最早消息，同时补齐离线新增消息；以第一页快照的流身份和游标重新订阅，接收分页期间的更新。分页重同步会废弃并发的旧分页响应，不只刷新最近 50 条消息。

客户端同时按事件游标与消息 `revision` 去重。发现版本缺口或缺少消息起点时，通过 `chat.get` 获取最新快照后继续。每个新回合创建新的聊天消息，实时详情与开场来源使用聊天消息 `id`，取消当前运行使用活动快照的稳定 `runId`；`attemptId` 继续用于公开流和骰子位置的版本校验，旧回合消息不会被覆盖。运行中详情保存在内存；历史推理、工具详情及模型信息从 Pi 会话按回合读取，公开消息保存用量和终态。结束回合的内存回退只保留最近八回合、合计至多 2 MiB；未写入 Pi 会话且已淘汰的详情不再可读。统计缓存仅保留模型摘要、工具次数和用量，不保留思考正文、参数或工具结果。

AI 聊天消息的 `pi` 保存原生 `sessionId`、`beforeEntryId` 和 `afterEntryId`，范围为 `(beforeEntryId, afterEntryId]`；会话身份防止文件替换后误认同名条目。运行开始前先保存初始边界，范围为空时两个端点相同；Pi 的普通消息写入成功后再保存结束条目关联。`SessionManager.appendMessage` 的监听包装仅在本次运行有效，结束时恢复原方法。Pi 与 SQLite 不构成跨文件事务；异常退出后，最后一条仍处于运行状态的消息在重开房间时补齐当前原生叶节点边界，再标为中断，不重新执行模型请求。

`PiHistory` 与 runtime 共享 `SessionManager`，详情直接通过 `getEntry()` 和 `parentId` 沿原生链读取该消息范围，不维护字节偏移或额外运行标记。脚本内的工具调用直接读取父工具结果上的 Pi 原生 `nestedCalls`，展示名称、SDK 保留的参数、状态及错误；Pi 不保存嵌套调用的完整返回值，应用不另建存储补写。摘要只保存工具次数与模型信息，以管理器为弱引用键缓存；`RoomMetrics` 只重新计算已变动消息的摘要，避免每次刷新扫描全部历史。已结束消息使用固定边界，后续模型调用不会串入先前详情。模型窗口等轻量信息保存在消息的 `modelInfo`；完整推理、直接工具调用的参数和工具结果仍保存在 Pi 文件中。首次缓存未命中时由 SDK 加载完整文件，房间关闭后释放管理器与摘要缓存。

会话统计由 `RoomMetrics` 管理，首次读取扫描存档，随后通过已提交通知在内存中标记变动消息，只更新这些消息的贡献；消息终态或用量校准会替换旧贡献，不重复累计。回滚事务不进入统计缓存，重开房间从存档恢复。每个角色只保留最近一次运行的模型信息，已离开队友的历史用量继续计入汇总。

`PublicAgentStream` 在流式消息携带的实测用量变化时发送 `usage` 快照，覆盖同一模型请求的用量，不累加快照；推理期间同样更新，且不公开推理正文。缓冲区约每 100ms 合并最新用量，模型消息结束时立即提交。新请求未返回有效上下文用量时保留最近读数；`PiHistory` 沿最近原生条目检查压缩边界，压缩后没有新实测用量时返回 `null`，重开房间仍按该边界恢复。统计不估算 Token。

房间投影在文档锁外读取统计，再按房间代数校验一致性；统计期间的文件 I/O 不阻塞文档提交，发生并发变化时重新生成投影。

本机使用 oRPC MessagePort，经 Electrobun 原生桥连接房主主进程。界面依赖游戏客户端契约，游戏路由与桌面设置、文件操作接口分离。房主统一排序、保存消息，每个房间最多一个 AI 运行。

## 配置与凭据

设置表单的自动保存、草稿与焦点行为见[界面设计](界面设计.md#设置与自动保存)。

玩家身份与游戏默认配置保存在 `~/.tarp/settings.json` 的 `game` 分组；自定义模型定义在 `models.json`，AI API Key 与订阅令牌在 pi 管理的 `auth.json`。主进程复用一份 pi `ModelRuntime` 提供服务商、模型目录、认证状态和实际请求；内置模型的上下文窗口、协议和能力直接采用 pi 目录，自定义模型使用 pi 的配置规则。每个服务商只保留一套配置，UI 保存同一服务商配置时更新已有凭据；自定义地址变化必须重新提供密钥。模型接口只返回脱敏投影，密钥不进入普通配置、聊天运行参数或房间资料。

模型运行时只初始化一次；每次业务读取重新加载磁盘配置并刷新，同一次操作的校验与返回投影复用已加载的配置和运行时。自定义模型定义写入或删除后显式刷新目录；登录与登出的凭据状态由 pi 同步，生成返回投影时复用已刷新的状态。

订阅令牌按 pi 的 `auth.json` 保存在配置目录，内容是明文 OAuth 凭据，目录 `0700`、文件 `0600`。前端只接收登录状态，不接收访问或刷新令牌。所有房间共用凭据存储的串行刷新锁，由 pi 在请求时自动刷新令牌。应用采用单实例运行，避免多个进程同时更新登录凭据。刷新失败时可在服务商的账号管理中重新登录。

房间目录的 `settings.json.ai` 保存服务商 ID、模型 ID 与展示信息，不保存 API Key 或订阅令牌。发送时按房间 ID 解析当前选择，应用的历史全局选择不参与请求。

房间模型切换从下一个 AI 请求起生效。公开聊天中只显示 AI 正文及简短状态，不发布内部推理、原始工具结果或模型异常原文。

房间的 `display.showReasoning` 统一控制主持人和 AI 队友的详情投影。开启后，队友正在考虑或最终未发言的回合也会显示，可展开同一套「推理与执行细节」查看模型返回的推理及工具记录；关闭后，这些内部回合恢复隐藏，正常发言仍保留。运行中的详情持续刷新，结束后可读取历史记录；模型未返回推理时不补写推理内容。

## 开发验证

从仓库根目录运行 `bun run test`、`bun run typecheck`、`bun run build`，包含游戏核心与桌面消费者。测试覆盖存档版本边界、Game State 原子提交与恢复、消息幂等与事务失败、双原生桥客户端收发和游标恢复、凭据隔离及 Pi 会话。真实供应商连通性需要在设置中提供有效凭据后验证。

上下文缓存的验收应同时核对稳定系统板块、历史前缀、输入量与未缓存输入量；不能仅凭缓存命中率百分比判断收益。
